# Forms module implementation ledger

This is a historical engineering ledger. The narrowed scope in [forms-release-scope.md](forms-release-scope.md) supersedes the original 20-section brief and its pending items. Account registration, new permission systems and reusable theme/template libraries are excluded. Production deployment of the scoped Forms release is authorized; destructive cleanup remains excluded.

## Architecture decisions

- Payload 3.87.0, official form-builder plugin 3.87.0, Next 16.3.3, Cloudflare D1 and R2 are installed. No tenancy model or production email provider is configured in the application.
- Extend the existing `forms` and `form-submissions` collections through plugin overrides. Keep existing plugin fields and submissions readable. A form uses either its versioned visual definition or the legacy plugin fields, never two active definitions.
- Keep pure schema, field registries, conditions, calculations, and rendering in `payload-design-core`; application adapters own authorization, D1 concurrency, storage, integrations, and Payload persistence.
- Use immutable published snapshots referenced by entries and resumable drafts. Native Payload versions retain authoring history. Public schema projection must strip private action settings and administrative metadata.
- Introduce an explicit site boundary with the existing site as default. Scope must be derived server-side, never trusted from public requests.
- All external providers have explicit configured/unconfigured status and deterministic local test adapters. Local capture/simulation is never represented as production delivery/payment.

## Current evidence

Initial inspection confirms the existing plugin's submission data is a string-valued array, public create is unrestricted by default, and its email hook runs immediately after creation. These defaults are insufficient for structured answers, immutable revisions and durable action dispatch; supported overrides plus a dedicated acceptance endpoint are required. No existing forms or submission data have been changed.

### Analytics and private-upload maintenance

Form authoring now includes an **Analytics and completion report** panel for users with entry access in that site. The public renderer emits only event kinds, configured field/step IDs, consent, an opaque event ID, and elapsed milliseconds through a revision-bound form session. Server projection discards other properties. No typed answers, file metadata, signatures, resume tokens, IP addresses, or account IDs are copied into analytics records.

- Views and starts are deduplicated per session/revision. Step entry and observed navigation/page-exit events count occurrences; page exits are best-effort browser delivery, not proof of abandonment.
- Validation events contain only known field IDs. Server validation records its own failures; the renderer avoids counting those returned failures a second time.
- Acceptance is recorded in the same D1 batch as the submission, with an idempotent event ID. Public analytics requests cannot supply an accepted event. Average time uses the stored start event; missing starts produce no duration.
- The dashboard filters UTC dates and calculates completion from starts and matching acceptances within the range. Estimated abandonment is explicitly labeled; visitors may complete later, and date boundaries may separate events. Telemetry waits for opt-in when required. Revoking consent stops subsequent collection but does not erase prior events.
- The authenticated dashboard endpoint checks site entry permission; anonymous requests are denied. Browser evidence verifies no collection before consent, measured validation errors, acceptance, no answer text in analytics rows, anonymous denial, and the actual dashboard report. Retention/purge controls, survey summaries, exports, and production-bundle coverage remain required work.

`FormPlatform.scanner` accepts a named `MalwareScanner` adapter with `scan({ bytes, mime, filename, signal })`. It must return `clean` or `rejected`; timeout, exceptions, or invalid responses produce `error` and quarantine the file. No scanner is configured in the default local setup, so uploads remain accurately labeled `unscanned`. The adapter tests use explicit test doubles; they do not claim external malware-scanning service delivery.

The authenticated job tick also runs bounded maintenance for expired/revoked drafts, expired temporary holds, and abandoned uploads. File cleanup first claims an expired, unsubmitted attachment as `deleting`, which prevents acceptance or renewal, then deletes only keys in that site's private form prefix. If object deletion fails, the record and object key remain for retry. Active uploads, accepted attachments, and other sites are preserved. Administrators can trigger the same maintenance with a same-origin POST to `/api/forms-actions/maintenance`. Submitted-entry retention and analytics purge are not yet implemented. ### Private exports and receipts

The form editor's **Export entries** panel requests CSV or real XLSX files with UTC date bounds, workflow-status filtering, selected answer columns, and an explicit sensitive-answer checkbox for authorized users. Stable column IDs accompany entry ID, original form title, revision, submitted timestamp, workflow status, and historical field-label metadata. Choices use historical labels; compound/repeated values remain structured JSON within cells. CSV formula-like strings are prefixed as text; XLSX strings use explicit inline-string cells with no formulas or macros. Workbooks use the [SpreadsheetML package structure](https://learn.microsoft.com/en-us/office/open-xml/spreadsheet/structure-of-a-spreadsheetml-document) and the local [fflate ZIP library](https://github.com/101arrowz/fflate).

Generation runs after the request and has a durable outbox record for recovery. It reads entries in pages of 100 with a maximum entry-ID boundary captured at request time. Original answers remain immutable; workflow status is read during generation, so this is not a transactional snapshot of changing review metadata. Default limits are 5,000 entries and 8 MiB of serialized row data, configurable through `FormPlatform.exportLimits`. Exceeding a limit produces an actionable failure instead of a truncated download. XLSX values beyond its per-cell limit require CSV or excluding that field. Final workbook assembly is buffered, not a streaming implementation; production Worker memory/load verification remains outstanding.

Export permissions are checked at request, generation, and download. Files are private, requester-bound, sensitive-permission checked, and expire after 24 hours. Users can return to **Forms → Form exports** for status and downloads. Maintenance removes expired objects while keeping metadata, retries storage failures, and reconstructs missing outbox records for interrupted pending requests. Failed exports can be requested again. The production scheduler still needs final integration and verification.

Entry details link to an escaped, script-free printable receipt with historical labels, structured values, matrix labels and drawn/typed signatures. The browser's Print command produces PDF output. Staff receipt access applies the entry/site/sensitive permissions. Submitters can prepare a receipt only using the original revision-bound session and its accepted receipt identifier; another session is denied. Public receipt preparation currently requires the owning form/revision to remain available and the original session to remain valid. No receipt is exposed by a public entry ID.

Export/receipt verification includes actual browser XLSX download and package inspection, sensitive-value exclusion, anonymous-download denial, another-session receipt denial, reopening the saved export job, and creation of `.wrangler/forms-receipt-test.pdf` with a reviewed PNG counterpart. ### Saved draft recovery and resume email

Published placements show the signed-in account's saved drafts for that form, with cursor pagination, original revision, expiry, Resume, and Revoke. Lists do not include answers or resume tokens. Anonymous progress uses the private link; account drafts additionally require the owning account. Resuming by account rotates the private token and invalidates the old link. A retired revision gives an explicit recovery message rather than silently upgrading answers.

Resume transfers the draft snapshot and all unsubmitted, unexpired files in one D1 batch with session/version guards. Concurrent stale resumes, revocations, and unavailable files cannot split ownership. Old sessions cannot overwrite a resumed draft. Client saves are serialized; changing the placement's form resets its private state. Submission stops further autosaving and replaces the editable form with its confirmation/receipt controls. Answers are not stored in browser storage.

The private-link area supports explicit revocation and **Email resume link**. Requests validate session, owner, revision, origin, token hash, and recipient, with per-session/IP and hashed-recipient rate limits. A durable `resume-email` action rechecks that the draft/link remains valid before delivery. Local development captures the email without external delivery; other environments require a configured Payload email adapter and reject the console adapter.

Private links are encrypted with AES-GCM in jobs and local captures, bound to the site and event ID with fresh nonces. Draft records retain only token hashes. Standard collection responses and action logs contain no plaintext resume tokens. **Forms → Local deliveries → Open protected message** exposes a local captured message only to integration-authorized users in its site; expired, revoked, or replaced links are refused. Captures are not evidence of external email delivery. Rotating `PAYLOAD_SECRET` makes old encrypted captures/jobs unreadable, so keep the secret stable while they are needed. External mail delivery is at-least-once with stable message IDs, not a promise of provider-side exactly-once delivery.

Eight focused tests cover atomic ownership transfer and authenticated encryption; the combined security/delivery/progress run passes 28 cases. Browser coverage exercises account recovery, encrypted local capture, private-message access, link rotation, and revocation alongside the existing anonymous upload/resume tests. Final production-bundle checks and the rest of the full module requirements remain outstanding.

## CMS record actions (local implementation)

The Actions tab now supports actual **Create contact**, **Create support request**, and **Create review content** executors. Choose compatible source fields visually; draft Posts also use a selector of available published Post Types. A contact maps email and optional name. A support request maps title, details, and optional reply email. A Post maps title and plain-text body and always starts as a draft attributed to the authenticated integration manager who approved the form.

Publishing these actions requires the site's integration permission. Approval is stamped by the server, replacing any client-supplied approver. Execution rechecks that user's current permission and uses access-enforced Payload writes. Source answers are loaded from the exact accepted entry/site/revision. Sensitive fields, descendants of sensitive containers, incompatible inputs, and fields inside repeaters are rejected as CMS mappings. Submitted HTML remains a text node in the generated rich text, never executable markup. Submitted values cannot choose a collection, author, role, or publication status.

**Forms ? Form contacts** and **Forms ? Support requests** contain private, site-scoped records linked to their original entry. ## Visual definition transfer and draft preservation

The builder now includes **Import / export form definition**. Administrators choose a JSON file, see validation errors without losing their current form, and explicitly confirm replacement. Replacement participates in the normal undo/redo history and document dirty state. Cancel makes no changes. The title, existing entries, and published revision are retained; imported field, option, and rule IDs are remapped.

Portable definitions exclude actions, payments, allowed origins, collection/profile prefilling, linked-group identifiers, and sensitive defaults (including sensitive values nested inside container defaults). Connections must be configured at the destination. Action-only rules are omitted. Imports reject unsupported versions, malformed shapes, oversized files, and invalid references. No submission data is included. This does not yet complete the reusable template/linked-group library requirement.

The transfer browser test exposed and fixed the builder's explicit **Save Draft** request: it now uses Payload's `draft=true` endpoint instead of changing the live document to draft. The passing browser flow covers invalid JSON, cancellation, confirmation, fresh IDs, undo/redo, actual download, draft save/reload, and an unchanged public revision. **40 Forms framework tests** pass, along with focused CMS/publication integration tests, type checking, lint, shared build, iframe asset generation, and the 18-registration guard. These remain local development checks; the local production Worker bundle and full-scope completion audit remain outstanding. No production action was performed.
